## 1. ZIP：修正が必要。ただしDeflateの説明を訂正する

対象は `ProjectPackageService.cs:308–313, 612–619, 623–669`。事前検査は `entry.Length` に依存し、JSON読み込みとサムネイルのコピーにアプリ自身の実バイト数制限がない。

.NET 8.0.31の実装では、Deflate展開にZIPヘッダの非圧縮サイズが渡され、Inflaterがそのサイズで出力を制限する。したがって「Lengthを128バイトと偽装したDeflateを最後まで無制限に展開する」という説明は、今回の環境では正しくなかった。

一方、無圧縮（Stored）のエントリは圧縮サイズの範囲を読み出すため、非圧縮サイズだけを小さく偽装するとアプリの制限を回避する。

現行ソースをそのまま取り込んだ検証プログラムで、実データ約64KB、申告サイズ128バイト、JSON・サムネイルの設定上限1KBとして確認した。

| 読み込み | Deflate | Stored |
|---|---|---|
| サムネイル | 128バイトで終了 | 65,536バイトを返す |
| JSON | 切断されたJSONとしてJsonException | 65,536文字の値を返す |
| 完全なプロジェクトをOpenAsyncで開く | 未実施 | 65,536文字のNameを復元 |
| 同じプロジェクトをValidateAsyncで事前検証 | 未実施 | IsValid=True、問題0件 |

小さい上限で制限回避を検証したものであり、実際のOOMを誘発した結果ではない。既定値はJSON256MiB、サムネイル1件4MiB、アーカイブ自体18GiBのため、無圧縮ファイルでも許容される入力サイズがメモリに対して十分大きい。これは高圧縮率を用いる典型的なZip Bombとは異なるが、資源上限の回避として修正が必要。

修正案はJSONに読み取り量を数えるラッパーストリーム、サムネイルに既存の `CopyWithLimitAsync` と実際の累積量検査を適用すること。Storedを含む不整合なヘッダについて、個別上限・合計上限と可能な範囲で宣言サイズの一致を検証する。レポートの「すべてをMemoryStreamへコピーしてからJSON解析」も上限回避は防ぐが、既定上限が256MiBであるため追加メモリを使う。読み取りを直接制限する構成が望ましい。

根拠：[.NET 8.0.31 ZipArchiveEntry](https://github.com/dotnet/runtime/blob/v8.0.31/src/libraries/System.IO.Compression/src/System/IO/Compression/ZipArchiveEntry.cs)、[Inflater](https://github.com/dotnet/runtime/blob/v8.0.31/src/libraries/System.IO.Compression/src/System/IO/Compression/DeflateZLib/Inflater.cs)。配布手順はframework-dependentであり、他の利用者環境のランタイム挙動まで今回の結果から保証しない。

## 2. OCR XML：上限の縮小だけでは不十分

対象は `NdlOcrCompanionService.cs:89, 301–335, 396–413`。ファイル全体を文字列へ読み、XDocument全体を構築した後でOCRページ数・行数を検査する。構文エラー時には正規表現と文字列結合による再試行もある。DTDは禁止されており、今回の問題はXXEではなく通常のXMLノードによる資源消費。

現行の取り込みコードに、100,000個の無関係な要素と1ページ1行のOCRを含む **1,500,108バイト** のXMLを渡した。ページ数上限1・行数上限1でも受理し、処理中のマネージド累積割り当ては約27.8MBだった。これはピーク使用量や保持メモリの測定ではなく、256MB入力時の消費量を一定倍率で推定できるものでもない。しかし、不要な要素も制限前に構築する設計は確認できた。

通常の読み込み元 `MainWindowViewModel.cs:3022, 3053` はサービスを直接awaitしており、`async`という名前だけではCPU負荷のUIからの隔離を保証しない。

XMLをXmlReaderで逐次処理し、全DOMを構築する前にノード数・深さ・OCR行数・文字数を制限するのが望ましい。キャンセルも解析中に確認する。短期策として16～32MiBへの縮小は候補になるが、長い文書の正当なOCRデータを拒否する可能性がある。「256MBは実用上想定されない」というレポートの前提は今回確認できていない。XML専用上限とJSON上限を分け、実データで互換性を確認してから決めるべき。

## 3～5. 外部プロセスへの引数

ログフォルダー起動は `MainWindow.xaml.cs:1081` でパスを引用符なしのArgumentsへ渡している。改善は小さいが、Explorer固有の解釈で空白が必ず分割されることは今回確認していない。パスは `ApplicationPathResolver` がアプリ配置先またはAppDataから生成するもので、PDFから任意コマンド文字列を受け取る処理ではない。

`PdfInputStructureService.cs:52–56, 86–90` は数値チェックなし。ただし入力はqpdfが解析・生成したJSONであり、通常の間接参照は数値の `O G R` 形式に限られる。PDF文字列には `u:` または `b:` の接頭辞が付くため、PDFに任意文字列を書くだけで自由な参照値を出力できるとは扱えない。`ExternalProcessRunner.cs:24–34` は `UseShellExecute=false` とArgumentListを使い、シェルによるコマンド連結はない。整数の構文・範囲検証を共通化する予防的な改善は妥当だが、レポートの例だけでは悪用を実証していない。

根拠：[qpdf JSONの参照と文字列の表現](https://qpdf.readthedocs.io/en/stable/json.html#representation-of-pdf-objects)。同梱版12.4.1の実動作は相対パスについてのみ検証した。

`PdfPageManagementService.cs:66–93` のパス未正規化は事実。同梱qpdf 12.4.1で、実在する `--input.pdf` を相対パスで渡すと未認識の引数として終了コード2、同じファイルを絶対パスで渡すと終了コード0になった。検証用の空PDFのみを使い、MaterializeAsync自体を起動した結果ではない。

通常の呼び出し元は `MainWindowViewModel.cs:3042, 4264, 4285–4290` などで解決済み絶対パスを渡しており、悪意あるPDFを開くだけでこの条件に至る経路は確認していない。予防的なAPI入力の正規化として修正を推奨する。ComposeAsync・RotateAsyncにも同じ入力方針を適用するのが自然。

## 6～7. 運用上の強化と診断モード

qpdfの環境変数優先は `PdfBookmarkService.cs:942–957` だけでなく `PdfExportService.cs:3532–3561` にも存在し、後者はPATH探索も行う。ページ管理の探索は同梱版を優先している。方針を変更するなら1か所だけでなく探索処理全体を統一する必要がある。

環境変数は起動時の実行環境であり、プロジェクト内の入力とは異なる。別ユーザーが対象ユーザーの起動環境を変更できる条件、あるいは異なる権限で動作する条件は今回確認していない。同じユーザー権限をすでに持つ攻撃者を想定する話として、即座に新しい権限獲得の脆弱性と断定しない。配布版では同梱版を優先する運用強化は合理的。

`App.xaml.cs:49–70, 105–116` の診断・ワーカー引数はReleaseにも含まれる。しかし比較は引数全体の完全一致。`C:\folder\--smoke-test.pdf` や `C:\folder\--smoke-test` は `--smoke-test` と一致しない。関連付けの documented command は実行ファイルと `%1` を引用符で囲んで渡す（`FILE-ASSOCIATIONS.md`）。通常のダブルクリックで名前が似ているだけのファイルが診断処理に入るという説明は根拠が弱い。裸の文字列 `--smoke-test` を手動で渡せば診断が起動するが、それは明示的なCLI操作。

特に `--isolated-pdf-export` とPDFネイティブワーカーの引数は、通常のPDF出力・ネイティブ処理を別プロセスで実行するために必要。`IsolatedPdfExportService.cs:105–110` は通常の出力でこの引数を渡す。テスト専用スイッチと一緒にDEBUGへ限定するとRelease版の機能を破壊する。整理するなら通常ワーカーモードを維持し、テスト専用モードだけを分ける。
