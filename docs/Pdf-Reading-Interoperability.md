# PDF読み方のリーダー互換性調査

2026-10-29。dev.269で現行方針を確定。比較実験の結果と採用判断を記録する。

## 採用する方針（dev.269）

利用者は「ノードドットjs」や短い間などの発音差を許容し、原文を保持する実用的な方式で進めることを了承した。現行のAlt＋言語情報の保存を継続する。本文・文字コード・ToUnicode・検索・コピーは読み方へ置き換えない。出力PDFの版も勝手に変更しない。

アプリ内の音声は共通辞書と行の例外を使う。外部リーダーでは元の表記から自然に発音される場合があり、登録読みの完全一致を採用条件にしない。ただし、比較結果は辞書や発音情報が使われた証明ではない。任意の登録語・固有名詞・すべてのリーダーで正しい読み方を保証するものではない。

出力完了では「保存した読み方情報」とその行数を表示し、外部リーダーでは発音や区切りが異なる場合があることを短く示す。効果の確認できていないPLS／Phonemeの追加や、新しい解析・保存工程は加えない。PDF 2.0での厳密な発音指定は将来課題として区別する。

以下は方針確定までの検証経緯。過去の不採用方式を実装済みと扱わない。

## 実機で判明した課題

最初の報告はBOOXのNeo Reader v3.0とAndroid版Adobe Acrobatで、`Node.js`に割り当てた読み方が反映されないというものだった。その後、下記のとおりPC版AcrobatとAudify 読み上げ Web ブラウザ（Android）での比較結果も受領した。dev.267／268は構造要素のAltとLang、MCIDとParentTreeを出力し、保存後のAlt再読込を検証している。実機の音声が読み方を利用することまでは確認できていなかった。

現在の出力は、かなの代替テキストをP要素へ関連付けている。発音辞書、ActualText、透明OCR本文の読み方への置換は行っていない。「読み方532行を保存」は保存・再読込の結果であり、これらのAndroidアプリで532行がそのとおり発音されることを意味しない。

## 利用者が確定した方針

- 全出力で、検索・コピーの原文を維持することを必須とする。
- 利用者は当初、任意の互換出力を許容したが、G／Hの実機結果の後に、透明OCR本文を置換してコピー文字が変わる方式は不可と明示した。最新の指示を優先する。
- 透明OCR本文の読み方への置換、および読み方をActualTextにしてコピー文字が変わる方式は採用しない。既定値だけでなく、選択式の互換出力としても実装しない。
- 読み方確認用のルビを紙面へ描画する方式には変更しない。

## 併記する情報と用途

| 方法 | 内容 | 原文への影響／制約 |
|---|---|---|
| Alt＋Lang | 代替テキストと言語。構造要素に加え、対象のSpan marked-contentへの指定も比較する | 原文の字形・文字コードを維持。利用するかはリーダー依存 |
| PronunciationLexicon | PDF 2.0の構造ツリーへ、PLS形式の読み方辞書を埋め込む。aliasで表記とかなの読みを対応付ける | 原文を維持。PDF 2.0の場合だけ。辞書対応はリーダーごとの実機確認が必要 |
| ActualText | 構造と対象Spanに代替文字列を指定する | 抽出・コピー・検索に影響するため、読み方の実装候補から除外 |
| 透明OCR本文の置換 | 画像に重なっている不可視OCR文字を読み方へ変える | コピー文字が変わるため不採用 |
| Phoneme＋PhoneticAlphabet | PDF 2.0の音素表記 | 適切な音素表記への変換と対応リーダーが必要。かなをipaと偽って書かない。今回の比較PDFには未使用 |
| E | 略語・頭字語を展開する情報 | 発音指定とは用途が異なるため、一般の読み方へ一律適用しない |

PDF 2.0の辞書キーは現在のPDF Associationの表にある`PronunciationLexicon`を参照する。出力バージョンを無断で2.0へ変更しない。通常のPDF 1.xにPDF 2.0専用情報を無条件で書き込まない。

## 実装前の検証

見た目がすべて同じNode.jsとなる、画像＋透明OCRの1ページPDFを6種類作成した。AはPのAlt、BはSpanとmarked-contentのAlt、CはB＋ActualText、DはB＋PDF 2.0辞書、EはC＋辞書、Fは透明OCR本文を読み方へ置換する。紙面画像はArtifactとし、読み上げの対象となる文字を一度だけ関連付けている。実アプリ全体の出力と完全に同じ構造を再現したものではなく、方式の違いを切り分ける最小例である。

6ファイルのqpdf構文検査、タグの親子関係、ParentTree、埋め込んだPLSのalias再取得を確認。Popplerで描画した6ページの画素はすべて一致した。PDFiumの本文抽出はA／B／Dが`Node.js`、C／E／Fが`ノードjs`となる。pypdfはC／Eでも`Node.js`を返し、Fだけ`ノードjs`を返す。抽出ライブラリごとに結果が異なることも確認した。これらは実機の音声確認の代替にはならない。

当時の判断ではFが互換出力候補だったが、コピー原文を必須とする最新指示により不採用となった。Eも不採用。Dは原文を維持するが、Audify 読み上げ Web ブラウザやBOOXが登録情報を利用したのか、元のNode.jsを自然に発音したのかは判別できない。D方式が全リーダーで読み方を強制できるとは記載しない。

PC版のFで末尾sが発音されなくても、コピー結果と本文抽出にsは存在する。音声側の解釈が原因の可能性はあるが、断定せず、英字を残さない読み方で切り分ける。

### 追加の最小比較

- G：Dと同じAlt＋辞書の組み合わせに、意図的に`Node.js → サクラ`を登録する。サクラと発音された場合に、少なくとも読み方補助情報のいずれかが使われたと判別できる。Altと辞書のどちらが使われたかまでは判別しない。
- H：F方式で、透明OCR本文をすべてかなの`ノードジェイエス`にする。長くなった不可視文字列が紙面外へはみ出さないよう収める。PC版の末尾欠落が英字混在の読み方に由来するか確認する。

両方とも見た目は同じNode.js。本体はdev.268のまま。

対象アプリの正式名称は「Audify 読み上げ Web ブラウザ」（Android）とする。Gではサクラという指定がいずれも読まれておらず、今回のAlt／PLS aliasを利用したことは確認できない。Hはコピー文字を変えるため、発音結果にかかわらず最新要件に不適合。

原文を残す候補としてPDF 2.0のPhoneme／PhoneticAlphabetと、PLSのphonemeを調べる。かなをIPAと偽らず、比較では有効なIPA `sakɯɾa`を手動で与え、サクラと発音されたかで判別する。これは任意の日本語／英字を自動的にIPAへ変換する実装を意味しない。ActualTextとOCR本文の置換は含めない。原文コピーを維持しても、これらのヒントを利用しないリーダーで発音を強制できるとは保証しない。

Iとして、PDF 2.0のSpanに`PhoneticAlphabet /ipa`と`Phoneme (sakɯɾa)`を指定し、同じ音素指定をPLS辞書にも埋め込んだ単一サンプルを作成した。AltもActualTextも付けず、透明OCR本文はNode.jsのままにした。qpdf構文検査、辞書と音素指定の再取得、描画を確認。PDFiumとpypdfの両方で抽出結果がNode.jsとなることを確認した。実機でのコピーと発音は未確認であり、採用済みとはしない。検証パスは`outputs/current-reading-phoneme-evidence.txt`に記録する。

いずれも判別用に指定したサクラは発音されなかった。今回のPhoneme／PhoneticAlphabetおよびPLS phonemeのサンプルで、読み方を利用した動作は確認できない。各アプリの全バージョン・全設定で未対応と断定するものではない。実機のコピー結果は今回の報告に含まれない。

現時点の結論：検証したリーダーとサンプルでは、検索・コピーの原文を維持しながら、PDF内の読み方情報だけで指定どおりの発音へ揃える方法を確認できなかった。発音用情報の保存・再取得は可能でも、リーダーがその情報を読み上げへ使うこととは区別する。コードを追加して対応済みとはしない。読み方で透明OCR本文やActualTextを置き換える回避策は、利用者の原文維持要件に反するため実装しない。

通常の文字抽出へ読み方を混入させる方法や、原文と読み方の二重の透明テキストを重ねる方法も採用しない。コピー・検索・読み上げの重複や混在を生む可能性があり、原文維持の代替にはならない。アプリ内の読み上げでは辞書を音声用テキストへ適用できるが、それを他社リーダーへ強制する仕組みとは区別する。

## 本体へ反映する際の要件

- 行の例外読みを共通辞書で上書きしない。PLSは文書全体へ作用するため、同じ表記に複数の有効な読み方がある場合は一律に辞書化せず、局所的な方法へ分ける。
- 使用していない辞書語や墨消しで除去した内容を埋め込まない。現在の墨消し・削除・出力対象判定と同じ経路で収集する。
- 複数文字オブジェクトに分かれた1行の読みを、各オブジェクトへ重複して付けて繰り返し発音させない。既存のタグや他の文字範囲を破壊しない。
- プロジェクトおよび出力PDFのOCR本文・文字コードを読み方へ書き換えない。検索・コピーの原文を維持する。
- 読み方をActualTextに指定せず、文字をかなで描き直したり、文書全体を画像化したりしない。
- 辞書は出力処理の同じトランザクションへまとめ、語ごとのPDF再保存や追加の全ページ解析を行わない。
- ファイル内の保存、文字抽出、実際の発音を別々の検査結果として記録する。PDF/UA準拠や全リーダー対応を表明しない。
