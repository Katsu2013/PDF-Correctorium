# v1.0.0-dev.215 — 実PDFで再現したOCR自動調整の修正

## 再現した原因

提供プロジェクトとPDFの物理7ページにある目次3行を、アプリと同じPDFium／1200px幅で検査した。編集済み座標と元座標の両方を使い、原ファイルは変更していない。

- 「コントローラーを作成する」のOCR点線は48点、画像は47点。「pages/hello.ejsを修正する」は51点と45点。dev.214は同数を必須にしたため、これらの行では点線補正を使えていなかった。
- 通常の推定でも、行頭から計算した字幅事前値の狭い累積候補範囲によって、本来の画像境界が選べなかった。逐字の再実行は更新済みの境界から残り領域を作るため、幅の目安が変わり結果が改善していた。
- 欧文の中空部分を境界に選ぶケースも実画像で確認し、英字の最小幅と字種事前値を調整した。

## 修正内容

1. OCR点数とは別に画像の規則的な点線を全範囲で検出する。妥当な点数差は本文・ページ番号のアンカーを維持し、点文字を実範囲へ均等配置する。原文・文字数は保ち、結果案内で双方の点数を示す。
2. 不規則な間隔、点欠落による分断、競合候補、大字形、大きな点数差は拒否する。長い点線の一部分だけを都合よくアンカーとして採用しない。
3. 共通の動的計画法で直前候補の境界と残り文字から幅の目安を更新する。狭い累積位置の強制をソフトなコストへ変更し、有界の探索帯と幅制約で計算量を抑える。行全体／選択文字以降／一括処理の共通推定器である。
4. 1回の画像投影・1回の結果適用を維持する。文字数回のコマンド実行やUI更新、全ページ画素コピー、永続キャッシュは追加しない。選択位置、選択前の境界、文字／領域ロック、単一Undo／Redoの契約を変更しない。

## 制約と互換性

画像からの幅推定であり、完全な文字認識ではない。点数不一致の点文字1個ずつは近似配置で、OCRの誤りは自動修正しない。接触文字、複雑な背景、不確かな点線は手動確認が必要。特定行の本文終端一致を、全PDFの全字形一致とは扱わない。

プロジェクト形式1.11／最低読込版dev.206、設定形式20、ボタン・アイコン・ショートカットは変更しない。設計Markdown原本を更新し、旧設計PDFは再生成しない。Gitコミット・push・公開は本作業に含まない。
