# RapidOCRによる未OCR領域への追加 — 実装前の仕様整理

2026-10-23更新。計画作成時のアプリはdev.232。選択行再認識はdev.233で余白付き1回・単一候補へ整理し、dev.234では認識余白と適用文字範囲を分離した。この文書の範囲・ページ・全体OCRは追加機能の計画であり、実装済み・ビルド済みの記録ではない。

## 確定した対象

- ページの一部をドラッグ指定、現在ページ全体、PDF／プロジェクトの全ページを対象にできる。
- 既存OCRの文字・幾何・固定状態・元データは変更しない。既存行の文字抜けは従来の選択行再認識で補完する。
- 初回から縦書き・横書きと、その混在ページを対象にする。行ごとの書字方向と読み順を別々に保持する。
- dev.232の選択行再認識・画像による文字幅調整は維持する。

## 提案する処理構成

1. 対象範囲を確定し、元PDFの画像だけを隔離ワーカーへ渡す。編集用の赤い文字や枠をOCR入力へ焼き込まない。
2. 文字領域を検出し、既存OCRと重なる行を除外する。削除予定領域の再生成や、既存の小さな文字枠による二重登録も防ぐ条件を検証する。
3. 残った領域の文字と書字方向を認識する。縦長の枠という理由だけで縦書きと確定せず、回転した横書き・短い見出しも検証対象にする。
4. 新しい文字枠を既存の編集モデルへ変換し、認識文字に合わせた文字送りを設定する。認識・幾何・読み順の推定は別の処理とする。
5. 既存行の相対的な読み順を維持しながら、新しい行の順序を提案する。縦組みの列、横組みの段組み、混在する見出しを単純なY座標順で混ぜない。
6. 追加の確定とUndoを既存の編集履歴に統合する。中止・失敗・文書変更の際に一部だけが黙って追加されないようにする。

## モデルと検証

現在同梱している日本語PP-OCRv4の選択行認識を、未検証の別モデルで一括置換しない。新規OCR用の検出モデル・認識モデルと必要な方向処理を別途評価する。

PP-OCRv5の公式資料には日本語・縦書き対応の記載があり、新規OCR用モデルの候補となる。ただし、本アプリの日本語縦組み・混在レイアウトでの実測は未実施で、対応や精度を保証したものではない。採用時にONNX・辞書の組み合わせ、ライセンス、固定ハッシュ、配布容量増分、既存ワーカーの資源上限を確認する。

- [PaddleOCR公式モデル仕様](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/module_usage/text_recognition.html)
- [RapidOCR公式モデル定義](https://github.com/RapidAI/RapidOCR/blob/main/python/rapidocr/default_models.yaml)
- [利用中のRapidOcrNetの実装](https://github.com/BobLd/RapidOcrNet/tree/708cae2fcb88720e1d891a81b5ee3e8b2bcc139e)

横書き、縦書き、縦横混在、段組み、句読点、縦中横、ルビ、回転ページ、既存OCRの部分的な存在、固定・削除予定の行を代表ケースにする。認識できることだけでなく、原画像の位置へ戻せること、方向・読み順・文字送りが保存／PDF出力後も保持されることを検証する。

## 軽快さと安全性

- モデルは操作開始時に初期化し、PDFを開いただけでは全文OCRを開始しない。
- ページ単位で処理し、全ページの高解像度画像を同時に保持しない。元PDFとモデルの再利用には上限を設ける。
- 進捗・現在ページ・中止操作をステータスバーで示す。検出中など総量未確定の段階と、処理件数が確定した段階を区別する。
- 結果一覧を設ける場合は仮想化し、原画像のプレビューは表示対象だけを遅延読み込みする。
- 原PDFは上書きせず、追加結果をプロジェクトと通常のPDF出力経路へ渡す。

## 確定した追加方針（2026-10-23のユーザー回答）

1. **結果の確定方法**：新規の枠・文字方向・読み順をプレビューで確認してからまとめて追加する。確認前にプロジェクトは変更しない。除外した候補は追加しない。
2. **ルビ**：本文と混ぜず独立したOCR枠として取り込む。親文字との構造的な関連付けは次段階とする。

この2点は確認済み。新規OCRの検出・方向・読み順・モデル評価とプレビュー画面は未実装であり、dev.236の外れ値フィルター／フォント通知修正には含めない。次の実装で上記ケースと資源上限を検証してから提供する。
